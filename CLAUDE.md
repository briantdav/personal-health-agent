# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Personal AI Health Agent that analyzes Garmin/Whoop/Coros data along with a morning intake journal to derive insights and suggest training and nutrition protocol based on current health and fitness goals.

## Current state

Garmin data ingestion, a daily dashboard (with a morning-journal habit-tracker modal), a year-of-history trends page, an automatic daily Garmin sync (via `launchd`, see Architecture), a real today's-training-plan card (run workouts only — pulled from the Garmin calendar, itself fed by a TrainingPeaks→Garmin sync that isn't fully reliable yet), and a mobile/PWA layer (installable on a phone home screen, served persistently, meant to be reached over Tailscale — see Architecture) exist; `src/agent.py` (the intended orchestrator/recommendation entrypoint) is still an empty placeholder, as is Whoop/Coros integration, non-running workouts (strength is logged in a notes app, not synced anywhere queryable yet — a planned Google Calendar-based route was discussed but not built), nutrition tracking, gamification (streaks/badges — discussed, not built), Google Calendar's day-snapshot, Slack follow-up recall, and turning journal + Garmin data into actual insights. The planned shape for that last piece: the daily *sync* stays a scheduled/deterministic job (no LLM involved, what's already built), but journal/Garmin → insights will need to be a *user-triggered* flow (e.g. calling the Claude API right after the journal form submits) rather than another scheduled job, since it depends on text only the user can write each morning.

## Commands

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

pytest tests/ -v                        # run the test suite
pytest tests/test_metrics.py -v         # run a single test file
uvicorn src.web.app:app --reload        # dev server at http://127.0.0.1:8000 (/ and /trends) — see note below
python -m src.tools.garmin              # print today's raw Garmin snapshot as JSON (auth smoke test)
python -m src.history.sync --days 365   # backfill data/history.db for the /trends page (see below — slow)
python -m src.history.daily_sync --force  # on-demand equivalent of the automatic daily sync
tailscale serve status                  # check the phone-facing HTTPS URL (see Architecture)
```

**Port 8000 is normally occupied by a persistent `launchd`-managed server** (`com.personalhealthagent.server`, not `--reload`), so your phone always has something to reach. For local dev with `--reload`, stop it first: `launchctl unload ~/Library/LaunchAgents/com.personalhealthagent.server.plist` (reload when done — see `scripts/com.personalhealthagent.server.plist`).

First run of anything that touches Garmin will prompt interactively for email/password/MFA (or read `GARMIN_EMAIL`/`GARMIN_PASSWORD` from `.env` — copy `.env.example`). OAuth tokens are then cached to `~/.garminconnect` (or `GARMINTOKENS`) so subsequent runs don't re-prompt.

## Architecture

**Garmin has no self-serve API for individuals** — the Connect Developer Health API requires applying as a legal entity. `src/tools/garmin.py` works around this with the unofficial [`python-garminconnect`](https://github.com/cyberjunky/python-garminconnect) library, logging in as your own Garmin Connect account the way the mobile app does. This is the pattern for any future per-source integration (Whoop/Coros): a thin wrapper module in `src/tools/` around whatever unofficial or official client exists, exposing plain functions keyed by date rather than raw API responses.

Layers, in order of raw → shaped → presented:

1. **`src/tools/garmin.py`** — raw Garmin Connect data.
   - Single-day functions (`get_sleep`, `get_hrv`, `get_training_readiness`, ...) accept an optional `date | str | None`, normalized via `to_iso_date`. `get_daily_health_snapshot()` aggregates everything for one day, catching `GARMIN_ERRORS` per-endpoint so one flaky endpoint doesn't take the rest down — reuse that tuple (and that catch-per-field pattern) for any new aggregate rather than catching bare `Exception`.
   - Bulk-range functions (`get_sleep_range`, `get_rhr_range`, `get_hrv_range`, `get_vo2max_range`, `get_body_battery_range`, `get_activities_range`) exist because Garmin has genuine range endpoints for these — one call covers up to ~a year. **Training readiness/recovery has no range endpoint**; pulling its history means one call per day (see `src/history/sync.py`).
   - `get_scheduled_workouts_for_month(year, month)` — Garmin's calendar (month granularity only, no day-range endpoint). This is how the dashboard's training-plan card gets today's scheduled run: filter `calendarItems` on `date`, `itemType == "workout"`, and `sportTypeKey == "running"` (see `src/web/metrics.py`'s `_scheduled_run`). A *completed* run that day shows up too, but as `itemType == "activity"`, not `"workout"` — the filter is what keeps those apart.
2. **`src/history/`** — the local cache the trends page reads from, so a year of daily data across ~10 metrics doesn't mean hitting Garmin (slowly, and rate-limit-riskily) on every page load.
   - `db.py` — SQLite (`data/history.db`, gitignored), one row per calendar date, columns nullable (a day with no logged activity is `NULL`, not `0`). `upsert_day()` merges fields from different syncers without clobbering columns it wasn't given.
   - `sync.py` — orchestrates a backfill over an arbitrary date range: bulk-range calls for most metrics, plus the slow paced per-day loop for recovery (commits every 10 days, so `Ctrl+C` mid-backfill doesn't lose progress). Run via `python -m src.history.sync`.
   - `daily_sync.py` — **the automatic daily sync**. Garmin has no push/webhook for individual accounts (the official Health API partner program that supports push is business/legal-entity only), so this approximates one: a `launchd` job (installed from `scripts/com.personalhealthagent.dailysync.plist` into `~/Library/LaunchAgents/`) invokes it every 20 minutes between 5:30–11:00am. Each invocation is a cheap, idempotent no-op unless it's both in-window *and* today isn't synced yet *and* Garmin actually has today's sleep data — so frequent invocation is fine, and there's no long-lived polling process to keep alive across sleep/wake. Logs to `data/daily_sync.log` (silent when it no-ops). Manual on-demand equivalent: `python -m src.history.daily_sync --force`. See the `garmin-sync` skill (`.claude/skills/garmin-sync/`) for the full on-demand/troubleshooting command set.
3. **`src/journal/`** — the morning journal habit tracker, storage-only (mirrors `src/history/` but for user-entered data, not Garmin-synced). `db.py` owns a `journal_entries` table in the *same* `data/history.db` file (different table — habits are joinable against Garmin metrics by date later, without being conflated with synced data). `save_entry()` is a plain upsert primitive, same merge semantics as `history/db.py`'s `upsert_day`.
4. **`src/web/journal.py`** — one `QUESTIONS` list (key, label, `bool`/`number`/`time`, optional `show_if` for a conditional field like "how many drinks?" only mattering if "drink alcohol?" is yes) drives the modal form, the submit parser, *and* storage, instead of hardcoding ~14 near-identical fields in multiple places. `parse_form()` makes the "submitted" semantics explicit: an unchecked HTML checkbox is simply absent from form data, so its absence means `False`, not "unanswered" — and a `show_if` field gets cleared to `None` server-side if its parent isn't true, even if a stale value came through, so editing "drink alcohol? No" on a resubmit can't leave yesterday's drink count behind.
5. **`src/web/metrics.py`** — the dashboard view model, and the one place that reads *both* live Garmin data and `src/history/db.py` (everywhere else picks one or the other). Sleep hours, sleep score, REM/deep sleep, body battery, recovery score, and HRV are keyed to `day` (Garmin already attributes the overnight sleep/morning readiness reading to the wake-up date); miles and workout time are keyed to `day - 1` — a summary of yesterday's training, not an in-progress live count — and every 7d/30d window (both directions: totals for miles/workout, trailing averages + up/down/flat trend for the other four) is anchored to that same `day - 1`, so nothing mixes a partial "today" into a rolling window. `_running_miles()` only counts Garmin's running family (`garmin.is_running_activity`) — golf, walks, rides etc. have a GPS distance too, but aren't running mileage; `_workout_hours()` deliberately counts every activity type. `_ring_band()` buckets a 0-100 score (sleep score, body battery) into the same four-tier scheme (90+ Excellent, 75-89 Good, 60-74 Fair, <60 Poor), reusing this project's four status tokens for the ring color — a `status` (for CSS) and a `label` (the tier name) are separate because "good" is both a status-token name *and* one of the tier labels for a different threshold. `get_todays_training_plan()` shows today's scheduled run from the Garmin calendar, or "Rest Day" if nothing's there (a real rest day, or the TrainingPeaks→Garmin sync hasn't caught up — both look the same from here, and that's fine for now). Run workouts only — strength/other workouts come from a different source once that's built, and this card doesn't know about them yet. This is *not* `src/agent.py`'s real recommendation logic (an LLM synthesizing recovery+journal into advice) — it's a display of an externally-authored plan; those are different, complementary things and both may end up on this card eventually.

   Because "running-only miles" changed what `daily_metrics.miles` means, `src/history/sync.py`'s `_sync_activities` needed the same filter — **a resync (`python -m src.history.sync --days N --skip-recovery`) was required** to correct historical values under the new definition; `--skip-recovery` keeps this fast since recovery data is unaffected and is the only part of a full sync that's slow.
6. **`src/web/trends.py`** — reads `src/history/db.py`, fills date gaps with `None`, forward-fills VO2 max (Garmin only emits a new reading occasionally, not daily), and rolls up into weekly/monthly series. Volume metrics (`miles`, `workout_hours`, in `SUM_METRICS`) aggregate as a **sum** ("weekly mileage"); everything else averages — mislabeling a runner's weekly mileage as a daily average would be actively misleading.
7. **`src/web/app.py`** — FastAPI app.
   - `/` + `/api/metrics` — the "Personal Health Portal" dashboard, greeted by `greeting()` ("Good morning/afternoon/evening, `$USER_NAME`" — set that in `.env`, or it just omits the name). Laid out as two sections: **Sleep & Recovery Snapshot** (Sleep — ring + sleep time + REM/deep breakdown; Recovery — score/badge + Body Battery ring; HRV — its own tile) and **Yesterday's Recap** (Total Activity, with Miles rolled up as a sub-metric beneath it). Plus the journal modal (`dashboard.html` renders it inline from `journal_questions`/`journal_values`, hidden by default) — its JS auto-opens on load unless today's already submitted (`journal_already_submitted`) or dismissed this session (`localStorage["journal-dismissed-<date>"]`); reopen anytime via the 📝 header icon. Journal submits via `fetch` to `POST /journal` (no page reload); needs `python-multipart` installed for form parsing.
   - `/trends` + `/api/trends` — small-multiple line charts (`src/web/static/trends.js`, vanilla SVG, no charting library), one per metric, with a Daily/Weekly/Monthly toggle and a collapsible data table (the WCAG-clean fallback). Shows an empty-state pointing at the sync command if `data/history.db` hasn't been populated yet.
   - Styling in `src/web/static/style.css` follows this repo's data-viz conventions: light/dark via `data-theme` + `prefers-color-scheme`, status colors reserved for state (never a categorical color) — including the dashboard's progress rings, which is why they reuse the same four tokens rather than a separate ring palette. **Never set a status-warning/status-serious hex as text color directly** — palette.md documents those as too low-contrast to read as text on a light surface; the ring band label and the recovery status badge both use the same mitigation (a small colored dot + neutral-ink text), not colored text. Single-hue accent line + recessive hairline gridlines for the `/trends` charts. Watch the `[hidden]` gotcha if adding more overlays/modals: an author-stylesheet class rule like `.modal-overlay { display: flex }` beats the browser's default `[hidden] { display: none }` unless you add an explicit `.modal-overlay[hidden] { display: none }` override (higher specificity) — already done for the journal modal.
8. **Mobile / PWA layer** — everything here exists so the dashboard is a real phone app, not just a page that happens to render on a small screen.
   - **`src/web/templates/base.html`** — every page (`dashboard.html`, `trends.html`, and any future one) extends this via `{% extends "base.html" %}` / `{% block title/head/body/scripts %}`. It owns the PWA `<head>` tags (manifest link, apple-mobile-web-app meta tags, `viewport-fit=cover`), the theme toggle, and service-worker registration — a new page gets all of that for free just by extending it. **Gotcha already hit once**: don't write literal `{% %}`/`{{ }}` character sequences inside an HTML comment or JS comment anywhere in a template, even describing Jinja syntax in prose — Jinja parses the raw text for those delimiters regardless of surrounding context, so e.g. writing `{% block scripts %}` inside a `<script>` comment breaks the block structure. Describe it in plain English instead.
   - **`src/web/static/manifest.json`** + **`src/web/static/icons/`** (192/512/180px PNGs, generated once with Pillow — not a runtime dependency, `pip uninstall`d after) — what makes "Add to Home Screen" install a real app icon instead of a bookmark.
   - **`src/web/static/sw.js`** — a minimal service worker (caches static assets only). Exists for installability and faster static loads, **not** offline data — dashboard/trends/journal requests are always network-first, since showing stale recovery/sleep numbers from a cache would be actively misleading.
   - **Mobile CSS conventions**, apply these to anything new: touch targets ≥44px (`.icon-button` is 44px); form inputs need `font-size: 16px` minimum or iOS Safari auto-zooms the page on focus; `.tile-row` forces a single column under 480px (`auto-fit` alone still crams 2 cramped columns in on a phone); `body` carries `env(safe-area-inset-*)` padding for the notch/home-indicator when running standalone. The journal modal's habit rows are `<label>` elements wrapping their input directly (not a separate `<label for>` + sibling `<input>`) specifically so the *entire row* is one tap target, not just the text.
   - **`src/web/static/trends.js`** handles touch the same as mouse (`touchstart`/`touchmove`/`touchend` alongside `mousemove`/`mouseleave`, sharing one `showTooltipAt()`/`hideTooltip()` pair) so scrubbing a chart works by dragging a finger, not just hovering a cursor.
   - **Two `launchd` LaunchAgents** now exist (`scripts/*.plist`, installed into `~/Library/LaunchAgents/`): `com.personalhealthagent.dailysync` (the existing Garmin sync check) and **`com.personalhealthagent.server`** (`RunAtLoad` + `KeepAlive`, keeps `uvicorn` bound to `127.0.0.1:8000` running persistently — no dev-server-in-a-terminal required for the phone to reach it). **`tailscale serve --bg --https=443 localhost:8000`** is what actually exposes that to your phone: HTTPS (required for real PWA installability, not just a bookmark) over your private tailnet only, terminated locally by `tailscaled`, no port-forwarding or public exposure. `-bg` makes it survive reboots without re-running the command. Tailscale itself (account + app on Mac and phone) has to be set up interactively — that part isn't something this repo or Claude Code can do for you.

`data/` (including `history.db`) is gitignored except `.gitkeep` — never commit real data there.
